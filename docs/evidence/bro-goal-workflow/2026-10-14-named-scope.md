The actual v4 baseline q25 changes Chrome while asking to reproduce Safari. Its [failed original result](2026-10-14-input-corpus-v4-durable-results.json) remains unchanged. No scope annotation is broadened to fit that effect.

The runtime now selects a bounded modification scope before generating a complex interpretation when the original input potentially refers to a task. ID/title tokens and relative-reference words only trigger the metered reasoning request; they never select the target or authorize effects. Explicit `/task` and `/decision` retain their existing hard boundaries. The scope response selects Goal, a finite existing task set, no requirement change, or unknown. It cannot invent task identities or silently convert unresolved references to Goal scope.

The committed binding records the original input ID, source requirements version, associated actual reasoning request and bounded hash-identified evidence. Core validation rejects Goal objective changes and independent task updates outside a selected task set; dependency invalidation remains runtime's job. It rejects mismatched input/version, unavailable/duplicate tasks and requirement changes under no-change/unknown scope. Typed-only or unacknowledged semantic results cannot mint bindings. Legacy snapshots omit the optional field. Unknown modification scope retains a change question and can preserve separately explicit valid control, without granting permissions or implying completion.

The UI reports the recorded boundary separately from authorization, dispatch and adoption, with a read-only evidence reference. Scope model calls use the same persisted native work, budget and acknowledgement path as other reasoning calls. There is no fabricated System One confidence or calibrated direct-control threshold.
