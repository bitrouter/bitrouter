# 命名 Provider Connection

状态：**提案，供审阅。未实现。** 本文不是当前支持的配置或服务格式，也不构成兼容性承诺。要求用语：必须、不得、应当、可以，分别对应 MUST、MUST NOT、SHOULD、MAY。

审阅通过之后，配置规则并入 [配置格式](configuration/README.md)，relay 与发布隧道的报文并入 [服务 API](service-api/README.md)，行为边界并入 [网关指南](../development/gateway.md)。并入时同时提交 schema、示例和兼容性用例，然后删除本文。在此之前，不得把本文中的字段当作生成 schema 之外的第二份字段目录来实现。

## 读者

独立演化、因此需要事先约定的读者有四类：

- 已经持有 `bitrouter.yaml` 的操作者。新读者必须接受今天没有发布块的文件；旧的严格读者遇到新增键时会失败，这个不兼容必须在并入配置规范时显式审阅。
- 通过网关提交 Chat Completions、Responses 或 Messages 的调用方。他们继续使用这些既有入口。
- 自托管 relay 与发布模型的网关。两边可以独立升级，断连和吊销之后仍须识别同一次请求。
- SDK 与 `bitrouter-ai` 的后续实现者。运行时和配置留在应用内，公开报文放在 `bitrouter-ai`，客户端方法放在 SDK。本文只规定语义；具体 DTO 在并入服务 API 时一起审。

## 决定

1. 推理请求只有一条执行链，就是网关管线。可选的语义路由先选定模型。`inference_routing` 启用时，scheduler 只在该模型的合格 connection 之间调度。gateway executor 是唯一有权证明「已经向上游发送」和「终态已知」的组件。
2. Connection 是现有 provider 与 account 的稳定名字。端点和凭证从那里派生。Connection 上不得再放一份 API key 或第二份 base URL。
3. 同一 connection 有两个方向。消费：用户的网关直连本地或远程 custom provider。发布：模型所在的网关主动拨出认证隧道；relay 在链接建立后调用已经显式发布的端点。
4. 产品路径不提供另一套推理服务。调用方进入网关的既有协议路由。本地引擎的指标只作为调度压力。崩溃后仍可能在执行的发送，必须记在这条执行链的 reservation 上。
5. 协议适配留在网关既有的 Chat Completions、Responses、Messages 适配器。隧道只搬运这些报文，不定义第三种对话方言。
6. 终态未知的推理不得自动重放，也不得借 fallback 再送一次。
7. 消费和自托管发布都不需要 Cloud 账号。发布端点不产生市场挂牌。Cloud 继续负责托管资源、租户权限、凭证托管和计费；那些不在本文范围内。

## 范围

本文覆盖 connection 的身份与派生规则、消费方向、可选的出站发布、relay 的授权和重放边界，以及这条执行链上的未知结果。

以下内容不在本文范围内：

- 语义路由如何选择模型，以及 provider 内部如何调度副本。
- 目录 OAuth。`bro providers login` 仍是目录登录，不是本文的发布链接。
- 共享网关的跨进程调度、marketplace、配对售卖，以及 Cloud 托管 relay。
- tenant 按请求解析凭证。第一份行为只覆盖启动时可以解析的静态 connection。
- 性能预算和策略比较实验。

## 术语

| 术语 | 含义 |
| --- | --- |
| Connection | 一个 provider，或多 account provider 中的一个 account。身份稳定，端点由其配置派生 |
| 消费 | 用户网关按派生端点，用既有执行器直接访问该 connection |
| 发布 | 持有模型的网关把选中的 connection 经出站隧道登记到 relay |
| Relay | 操作者自托管的转发点。它核对接通范围，并把调用送回发布侧网关 |
| 执行链 | 网关入口、可选的语义选模型、可选的 scheduler、协议适配、executor 发送 |
| 未知结果 | executor 已经可能向上游发送，但没有拿到可证明的终态 |

## 执行链

一次生成按下面的顺序通过网关：

1. 入口完成鉴权，并把请求规范成既有的管线输入。
2. 构建启用了语义路由时，由它选定一个模型并冻结协议约束。调用方已经指定模型时，跳过这一步。
3. 解析该模型的合格 connection。
4. `inference_routing.enabled` 为真时，在路由钩子冻结成员之后进入 scheduler：入队、按租户公平出队、排名、预订容量。为假时，沿用今天的静态路由链，不分配队列、reservation 或 prefix 状态。
5. 协议适配器生成上游请求。
6. executor 在真正开始 poll 传输之前记一次发送。这个时刻之后，取消、超时、截断和传输中断都是未知结果。
7. provider 自己的服务负责副本。BitRouter 不在 connection 之间拆副本。

调度关闭时，既有 fallback 策略保持原样。调度开启时，超时、截断、取消、传输丢失和未知结果禁止 fallback；只有明确拒绝或证明尚未发送的结果才可以进入既有 fallback，而且 fallback 仍可以拒绝。已经验证完成的响应，即使客户端没有收完，也禁止 fallback。流一旦建立，不得换一条上游重开。

本地压力观察、暂停或指标过期，只能作用于这条链上的准入。它们不得另开监听地址来接收推理请求。

## Connection

单凭证 provider 的 connection id 就是 provider 名称。多 account provider 的 connection id 由 provider 名称和 account 标签组成；标签为空时，使用配置里已经派生的 `account-<n>`。id 在一份配置内必须唯一。端点不得编进 id。

每条 connection 必须能从现有配置派生出：

- 一个端点，即该 provider 的 `api_base`，或该 account 的非空覆盖；
- 一个凭证引用，即对应的 `api_key`，形式保持今天的环境变量引用；
- 一组模型绑定，即该 provider 声明或发现的模型；
- 一组协议，即该 provider 现有的 `api_protocol` 规则。

Connection 不得携带自己的密钥、base URL 或协议枚举。account 只改变凭证和可选端点；模型、协议和限流仍属于 provider。

下面的片段只说明派生关系，不是字段目录：

```yaml
providers:
  studio:
    api_base: http://127.0.0.1:8000/v1
    api_key: ${STUDIO_KEY}
    models:
      - id: model-one
```

这里的消费 connection id 是 `studio`，端点是 `http://127.0.0.1:8000/v1`。

`inference_routing` 进入配置规范时，目的地必须引用 connection 和模型，并带上该目的地的 `max_active`。目的地不得再写 provider、endpoint 或 account。启用调度时，每个可能被派发的合格目标都必须有对应目的地，否则整份配置在启动或重载时失败。普通模式在启动时完成解析。本文不要求按请求重新解析 tenant 凭证。

同一 connection id 的端点或隧道对端地址发生变化时，不得更换 scheduler 的容量池 generation。已经预订的尝试仍发往预订当时解析到的端点。此后的新尝试使用新端点。未知工作继续记在这条 connection 上。成员集合或容量变化仍按 scheduler 既有的冷变更处理：不能热更新的字段拒绝整次重载。

## 消费

消费方向是网关到 custom provider 的直接 HTTP，本地地址和远程地址使用同一条规则。不经过 relay，也不需要 Cloud 账号。

操作者必须能够对一条 connection 做三件事：列出它的派生身份，用既有的模型列表接口发现模型，以及做连通性检查。检查必须确认凭证引用可以解析，并按该 connection 的协议取得模型列表。检查不得提交生成请求，不得因此占用 scheduler 容量。

发现和检查使用既有的认证、超时和流式实现。模型列表的成功只说明端点按该协议回答了列表，不证明每个模型都能完成生成。

## 发布与 relay

发布默认关闭。省略发布配置的 provider 只作为消费 connection 存在。开启发布时，操作者必须显式列出要发布的模型；空列表不得解释成「全部模型」。

持有模型的网关主动向操作者指定的 relay 拨出隧道，并出示发布令牌。发布令牌是环境变量引用，与上游 `api_key` 不是同一个秘密。网关在隧道上声明 connection id、选中的模型，以及既有协议。relay 把这份声明绑定到该令牌的授权范围。

远程调用方另行向 relay 认证。调用方凭证、发布令牌和上游 provider 密钥必须是三份不同的秘密。relay 不得看到或保存上游密钥。上游密钥只在发布侧 executor 访问 provider 时使用。

relay 接受调用之前必须确认：调用方凭证有效，发布授权没有吊销，目标模型在本次声明的集合内，请求协议是 Chat Completions、Responses 或 Messages 之一。然后把请求交给发布侧网关的普通入口。发布侧网关走上一节的执行链。relay 不得自己排名，不得选择另一个 connection，不得把报文转译成另一种对话协议。

推理载荷沿用对应协议的 JSON 或 SSE。relay 转发既有的 `x-bitrouter-timeout-ms`：它表示普通生成的剩余时间预算，不赋予租户或执行权限。托管、tenant 和 native 执行继续拒绝这个头。头的存在不证明上游已经取消。

发布令牌被吊销后，relay 必须立即拒绝该授权上的新请求。已经交给发布侧的请求按下一节处理，不得因为吊销就删掉 request id。

隧道地址变化不改变 connection id，也不抬高容量池 generation。

## 请求身份、未知结果与重放

发布路径上的每个请求必须带调用方提供的 request id。relay 对它接受的精确请求字节计算 SHA-256，发布侧在发送前核对同一摘要。

在同一发布授权内：

- 相同 request id 与相同摘要必须返回已保留的状态。已知完成则返回该结果；仍然未知则返回未知。两种情况都不得再向上游发送一次。
- 相同 request id 与不同摘要必须拒绝。
- 摘要覆盖的是 relay 接受的请求字节，不是适配之后的上游字节，也不是语义上重排过的 JSON。

发送证明只有发布侧 executor 一份。relay 在收到「尚未发送」时，可以重新投递同一次请求。它一旦收到未知结果，或者在可能已经发送之后失去隧道，就必须停止投递，并向调用方报告未知。relay 不能确认发布侧是否收到时，必须按 request id 查询，不得把它当成新请求提交。查询也失败时，调用方看到的结果是未知。

终态规则：

| 发布侧观察到的情况 | 容量与记录 | 允许的后续发送 |
| --- | --- | --- |
| 证明尚未发送，或上游明确拒绝 | 释放这一次预订 | 既有 fallback 仍可拒绝 |
| 终态已经验证，包括客户端没有读完的成功响应 | 释放 | 不得再发送 |
| 发送已经开始，之后超时、断流、截断或取消 | 记为未知 | 不得 fallback，不得自动重放 |
| 调用方在发送开始前取消 | 释放，且不得产生上游尝试 | 不得补送 |

未知记录到期只放下本地记账。到期不证明 provider 已经停止，也不产生重试资格。稍后到达的终态证据不得第二次释放同一笔占用。

本地引擎上的 connection 还必须把未知发送持久化。网关进程重启之后，同一 request id 与相同摘要不得再次发送；不同摘要仍然拒绝。启用调度时，这些持久记录继续占用该 connection 的容量。未启用调度时，记录只阻止重发，不因此创建队列。远程 provider 的未知结果保持进程内规则：重启不恢复这批占用，进程活着的时候仍然不得重放。

操作者可以显式核销一条已经确认不再运行的本地未知记录。核销必须核对 request id、摘要和当时的记录版本，并留下不同于「成功完成」的状态。核销之后该 id 不得再次执行。发布令牌和调用方凭证不得拥有核销权限。

恢复记录只保留 request id、摘要、connection id、状态和必要的时限。不得写入提示词、凭证或响应正文。

## 调度与本地压力

调度公式、公平队列和 prefix 观察属于网关实现的行为边界，并入时写进网关指南，不在本文重复第二份算法说明。本文只约束它们与 connection 的关系。

启用调度时，排名对象是该模型下当前可以预订的 connection。负载分只使用本进程已经预订、已经发送和未知的工作量，加上本次尝试的固定 charge，以及目的地配置的容量。prefix affinity 只能在既有的窄压力带内影响选择。

connection 可以声明一组本地引擎指标。指标缺失、过期、不完整，或者引擎标签对不上时，该 connection 的压力视为未知，不得当成零负载。指标里已经包含主要流量时，准入必须把本进程尚未结束的工作再次计入。重复计入会使准入更紧；在指标不能指出哪些尝试已经被统计时，这是规定的算法，不是误差。这些指标不得替换负载分，也不得被解释成剩余 GPU 容量。

未声明指标的 connection 只受 scheduler 自己的容量和未知额度约束。

## 兼容性

新读者读今天的配置：没有发布块、也没有 `inference_routing` 时，行为与当前静态路由一致。provider 名称和 account 标签继续是它们今天的身份。

旧读者读带有新键的配置：根对象今天拒绝未知字段。因此发布块一旦进入 schema，就是对严格旧读者的不兼容变更。并入配置规范时必须把这点写入该次 beta 修订说明。不得用默默忽略未知字段的方式让旧读者假装发布没有发生。

`inference_routing` 尚未进入当前配置规范。它进入时必须直接采用「connection + 模型」的目的地。若实现分支上已经出现重复书写 endpoint 的目的地，不得把那种元组静默解释成另一条 connection；需要迁移时必须是显式的操作者动作。

relay 报文并入服务 API 时，必须同时审阅旧 relay 接新网关、新 relay 接旧网关。未知的必填语义必须失败，不得改写成另一种传输或更弱的授权。请求侧在相应 schema 确定为拒绝未知字段之后，新增请求字段也要按不兼容变更审阅。

本文不给 `bitrouter.yaml` 增加格式版本号。发布是否开启由发布配置是否存在并且启用决定，不由文件版本决定。

## 安全边界

- 上游 provider 密钥不得出现在隧道、relay 日志或恢复记录中。
- 发布令牌只用于建立和维持发布。它不能调用推理，也不能核销未知工作。
- 调用方凭证只用于向 relay 提交已被授权的模型。它不能改发布集合，也不能取得上游密钥。
- 吊销和断连必须保留 request id 与授权边界。吊销不是删除历史身份。
- 共享网关模式不得因本文而获得跨进程 scheduler。
- 检查、发现和指标采集不得被当成执行授权。

1. 目的地只写 connection id 与模型，端点和密钥完全派生。
